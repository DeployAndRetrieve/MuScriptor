## 1. 目的と適用範囲

一般的な混合音源（MP3 など）から楽器別の音符イベントを推定し、譜面確認・手修正・MIDI／MusicXML 出力を行う。変換した MIDI と原盤を同時再生し、音量とミュートを独立操作して採譜内容を聴き比べる。

**基本方針**：採譜・再生・ファイル編集を Android 端末内で行い、推論サーバーおよびアプリからの音声アップロードを使わない。開発時のモデル取得・ソース取得・依存ライブラリ取得には PC とネットワークを使用する。

**現行の対象外**：PDF／紙の楽譜からの認識、既存 MusicXML のインポート、自動テンポ／拍子／調号推定、商用品質の浄書、独自 SoundFont 管理、サンプル精度のオーディオ同期、バックグラウンドでの常時再生、楽曲複数プロジェクト管理、学習済み重みの自動ネット配信。

## 4. 全体構成

```text
Android の SAF
    ├─ 原盤 MP3/WAV等の Uri ─→ AudioDecoder ─→ mono 16 kHz float[]
    │                                          │
    │                                   NativeBridge (JNI)
    │                                          │
    │                            libmuscriptorscore_bridge.so
    │                                          │ dlopen
    │                            libaudiocpp.so + GGUF モデル
    │                                          │
    │                               MuScriptor イベント JSON
    │                                          ▼
    │                                TranscriptionParser
    │                                          │
    │                              List<NoteEvent>（編集可能）
    │                                ┌─────────┼──────────┐
    │                                ▼         ▼          ▼
    │                             ScoreView  MidiExporter MusicXmlExporter
    │                                │         │          │
    │                             譜面表示    .mid       .musicxml
    │                                          │
    └─ 原盤 Uri ────────────────────────────────┤
                                               ▼
                                    ComparisonPlayback
                                      MediaPlayer × 2
                                      共通制御／個別音量
```

制御クラス `MainActivity` が画面、ファイル選択、バックグラウンド処理の起動、状態の保持と保存を担当する。推論は `Executors.newSingleThreadExecutor()` 上で実行し、UI 更新はメインスレッドへポストする。再生の操作・コールバックは UI スレッドで処理する。

| ファイル | 役割 |

## 5. データ設計

### 5.1 音符イベント

`NoteEvent` の論理項目：

| 項目 | 型 | 条件 |
|---|---|---|
| `instrument` | String | 楽器識別子（例：`acoustic_piano`、`drums`） |
| `pitch` | int | MIDI 音高 0〜127 |
| `startSeconds` | double | 曲先頭からの開始時刻（秒、0 以上） |
| `endSeconds` | double | 終了時刻（秒、開始時刻より後） |

ローカル保存 JSON の例：

```json
[
  {"instrument":"acoustic_piano","pitch":60,"start":0.0,"end":0.5},
  {"instrument":"electric_bass","pitch":40,"start":0.5,"end":1.0}
]
```

これはアプリ独自の保存形式。MuScriptor 生イベント JSON（`type=start/end`、`index`、`start_event_index`、`start_time`／`end_time`）とは異なる。

### 5.2 保存領域

| 対象 | 現行の保存先 | 備考 |
|---|---|---|
| 編集中の音符一覧 | `getFilesDir()/project.json` | 現行は 1 曲分のみ、上書き保存 |
| BPM | Activity Preferences の `bpm` | 初期値 120、設定範囲 20〜300 |
| 原盤ファイル | SAF から取得した Uri | 原本をアプリへコピーしない。Uri と表示名を Preferences に保存 |
| ユーザー導入モデル | `getFilesDir()/models/muscriptor-small-f32.gguf` | 一時ファイルを経て配置 |
| 比較用 MIDI | `getCacheDir()/muscriptor-preview-*.mid` | 使い終わったら削除 |
| 原盤／MIDI 音量 | Preferences の `original_volume`／`midi_volume` | 0〜100、初期値 100 |
| MIDI／MusicXML／JSON 出力 | SAF でユーザーが指定した Uri | アプリ内 DB には保存しない |

SAF の読み取り権限は可能な場合に永続化する。元ファイルの削除・移動や権限失効時には選び直しが必要。現行の編集プロジェクト保存には履歴管理・復元ポイント・多曲管理はない。

## 6. 採譜処理仕様

### 6.1 原盤の選択とデコード

1. 「MP3を選択」で `ACTION_OPEN_DOCUMENT` を起動する。実際は端末の対応デコーダで扱える音声形式を対象とする。
2. 原盤を切り替えた際は旧音符データと比較再生を破棄し、選択 Uri を保存する。
3. `AudioDecoder` が音声トラックを抽出して PCM に復号する。複数チャンネルは平均して mono に変換する。
4. 入力サンプルレートから 16,000 Hz へ線形補間する。
5. 再生時間が 10 分を超える場合はエラーとして終了する。

16 kHz × 600 秒の `float[]` は約 38.4 MB（10 進表記）を要し、さらにデコード中のバッファ・ネイティブ処理・モデルのメモリが必要となる。端末 RAM 量が実用上の制約となる。

### 6.2 推論の実行

1. モデルが `getFilesDir()/models/muscriptor-small-f32.gguf` にあることを確認。
2. `NativeBridge.nativeAnalyze(path, pcm, 16000, 2000)` を呼び出す。
3. JNI が `libaudiocpp.so` を `dlopen` し、C API シンボルを取得する。
4. MuScriptor ファミリでモデルを読み込み、CPU／2 スレッド・`midi`／`offline` のセッションを作る。
5. 出力形式 JSON、`max_tokens=2000`、サンプリング無効で推論する。
6. 返されたイベント JSON を `TranscriptionParser` で `NoteEvent` に変換し、保存・表示する。

**制約・リスク**：現在の JNI 実装は解析ごとにモデルをロードする。処理時間、メモリ使用量、長時間楽曲の 2,000 トークン上限、音符欠落、JNI ABI 整合性を実機で確認する必要がある。モデル・ランタイム未導入時は採譜できない。進捗表示は現状、不定の実行中表示であり、厳密な推論進捗率を示さない。

### 6.3 イベント変換

`start` を `index` で保留し、対応する `end` の `start_event_index` で終了時刻を結合する。音高が 0〜127 外のイベント、開始時刻が無効なイベントは採用しない。終了時刻が開始時刻以前または非有限の場合は、開始 + 0.06 秒として補正する。終了イベントのない開始イベントは結果に含めない。開始時刻→音高の順で整列する。

### 7.1 状態遷移

- 原盤未選択：採譜不可。
- 原盤選択済み・モデル未導入：採譜開始前に不足を通知。
- 採譜中：二重投入を防止し、ジョブを直列実行。
- 採譜完了：音符編集・出力・比較試聴が可能。
- 音符変更／BPM変更／楽器切替：比較再生をリセットし、次回再生時に MIDI を再生成。
- アプリ `onPause`：比較再生を一時停止。`onDestroy`：プレーヤーを解放。
- ネイティブ解析に失敗：エラー表示。正常な音符データを生成できていない場合は完了扱いにしない。

## 8. MIDI・MusicXML・比較再生設計

### 8.1 MIDI 出力

`MidiExporter` は SMF Format 1、PPQ 480 で出力する。先頭にテンポ／4/4 拍子のコンダクタートラックを作り、楽器ごとに楽器名・GM プログラム変更・Note On/Off イベントを持つトラックを出力する。ドラムは MIDI チャンネル 10（0 始まりの 9）を使う。ベロシティは現状固定 80。時刻は秒と手動 BPM を用いて tick へ変換する。

「全パート」選択時は 1 個のマルチトラック MIDI、個別楽器選択時は選択楽器だけの MIDI を作る。一括で楽器数分の `.mid` を個別ファイル化する機能は未実装。メロディ楽器がチャンネル数を超えた場合の割当再利用は音色競合を起こし得るため、改善対象とする。

### 8.2 MusicXML 出力

`MusicXmlExporter` は `score-partwise` を生成する。固定 4/4・手動 BPM・16 分音符グリッド（PPQ 480／GRID 120）に量子化し、重複音は別声部に配置する。小節境界や分割した音価はタイでつなぐ。

**未対応／制約**：原曲の可変テンポ、拍子・調号の自動推定、自然な連桁・休符の高度浄書、歌詞、信頼できる打楽器譜表現、PDF 直接出力。外部楽譜ソフトでの修正を前提とする。

### 8.3 原盤／MIDI 同時再生

`ComparisonPlayback` は Android `MediaPlayer` を 2 本使用する。

1. 現在表示中の `NoteEvent`（全パートまたは選択した 1 楽器）を一時 MIDI ファイルへ変換。
2. 原盤 Uri と一時 MIDI をそれぞれ `prepareAsync()` する。
3. 双方の準備完了後に同時再生を要求。
4. 原盤をマスタータイムラインとし、250 ms 周期の確認で、MIDI 側とのずれが 250 ms を超える場合は MIDI 側を `seekTo()` する。
5. 各音源の音量スライダーを独立適用。ミュートは実音量 0 にするが、設定音量を破壊しない。
6. 原盤が終了したら MIDI を停止。原盤より長い MIDI の末尾は再生しない。
7. 停止・パート変更・音符編集時に MediaPlayer を解放／再作成する。

この方式は**ベストエフォート同期**であり、2 つの発音機構・デコーダ・オーディオ経路の遅延差を完全には除去できない。Android 端末に Standard MIDI File を再生できる MediaPlayer 実装があるか実機で検証する。未対応環境向けの内蔵ソフトシンセサイザーは今後の代替設計とする。

## 9. モデル内包化の変更設計（未実装）

### 9.1 目標

利用者が初回起動時に「モデルを追加」を操作しなくても、正規に取得した MuScriptor Small を端末内で使用できるようにする。**アプリの実行にサーバー接続を必要としない**という要件を維持する。

### 9.2 方式とファイル配置案

```text
開発 PC（ライセンス確認・チェックポイント取得）
  └─ Prepare-Model.ps1 で GGUF 変換
       └─ 配布対象の許諾・整合性を確認
            └─ ローカルの非追跡アセットディレクトリ
                 app/src/main/assets/models/muscriptor-small-f32.gguf
                    ↓ ビルドへの組込み（要実装）
Android APK／配布物
  └─ assets/models/muscriptor-small-f32.gguf
       ↓ 初回起動または利用直前にチェックサム確認・必要時コピー（要実装）
getFilesDir()/models/muscriptor-small-f32.gguf
       ↓
NativeBridge → libaudiocpp.so
```

- **取得段階**：利用者・開発者が公式モデルの利用条件に同意した後に、チェックポイントを取得する。勝手な自動ダウンロード、資格情報や利用条件の回避は行わない。
- **変換段階**：`scripts/Prepare-Model.ps1` の GGUF 変換を利用する。変換成功・モデル形式の適合性を実測し、モデル名と SHA-256 をビルド対象メタデータとして記録する。
- **梱包段階**：ビルドは指定アセットが存在し、期待サイズ・チェックサムを満たすことを確認してから進める。欠落時は「モデル内包版」としてのビルドを**失敗**させる。モデルの実容量は変換物から取得し、固定の 412 MB 等を仕様保証値にしない。
- **端末段階**：専用ファイル領域の既存モデルをハッシュ／バージョンで確認する。不一致時は空き容量と書込み可能性を検証し、`.tmp` にストリームコピー→検証→置換する。成功後のみ採譜ボタンを有効にする。
- **再起動時**：正しいモデルが配置済みなら再コピーしない。コピー中断や容量不足はユーザーに明示し、壊れたファイルを使用しない。
- **画面**：内包モデルが正常に利用可能なら「モデルを追加」を通常画面から削除し、設定画面にモデル名・版・状態を表示する。開発／修復用の手動導入機能を残すかは別途決定する。
- **ネイティブランタイム**：`libaudiocpp.so` は別途 NDK ビルドして、適合する Android ABI の `jniLibs` に含める。**モデルだけ内包しても推論は動かない**。

### 9.3 配布・ライセンス

現時点で参照している MuScriptor コードは MIT、モデル重みは **CC BY-NC 4.0**、`audio.cpp` は Apache 2.0。モデルの取得・組込み・第三者への配布については、公式配布元の最新条件と権利者要件を配布前に確認する。個人利用の意図だけで、モデルを公開 GitHub や公開 APK に自由に再配布できると判断しない。

GitHub の公開リポジトリには GGUF／safetensors／署名鍵／ライセンス認証情報をコミットしない。`.gitignore` で `*.gguf` と `*.safetensors` は除外済み。公開 CI へ秘密の重みをアップロードする設計もしない。アセットの署名・配布方法は利用許諾に合わせて別途決める。

### 9.4 非機能・障害時仕様

モデル内包でアプリの配布サイズと端末保存領域が大きくなる。初回コピーでは APK 内のモデルと専用領域内のコピーが併存し、追加の空き容量を消費する。コピー前の空き容量チェック・原子性・ストレージ不足時の復旧を必須とする。Android のパッケージング制限、APK 配布方法、メモリ不足、ロード時間は実機で検証する。必要に応じて非圧縮アセット／ファイル記述子／mmap 等の方式を比較するが、現行 C API がパスを必要とするため、互換性が確認できるまでは専用領域へのコピーを基本案とする。

## 10. ビルド／構成管理

1. `git clone https://github.com/DeployAndRetrieve/MuScriptor.git` でソースを取得。
2. Gradle Wrapper 8.13（公式 SHA-256 検証済み）を使用。通常の Android コードのビルドは `.\gradlew.bat --no-daemon :app:assembleDebug`。
3. ネイティブ推論を利用する場合は `scripts/Prepare-Native.ps1` で `audio.cpp` の指定コミット `e74e0aaea1a9ed0d3dde4752c73670068f9c1ea4` を取得して Android ARM64 用共有ライブラリを作る（現行スクリプトは実機で未検証）。
4. 現行の手動モデル方式では、公式チェックポイント取得後 `scripts/Prepare-Model.ps1` で GGUF へ変換し、端末に転送する。
5. モデル内包方式が実装された後は、第 9 章のアセット検証を満たしてからビルドする。
6. インストール・起動・採譜・MIDI 音色・音声同期の各項目を実機で確認する。

ソース ZIP 名と解凍後ルートフォルダ名にはバージョン番号を含めない。バージョンは `app/build.gradle` の `versionCode`・`versionName` および設定画面で管理する。Git のブランチは `main`。第三者依存ソース、モデル重み、ビルド成果物は原則コミットしない。

## 11. 非機能要件と既知の課題

| 分類 | 要件・制約 | 対応／要検証 |
|---|---|---|
| プライバシー | 原盤・採譜データをサーバー送信しない | Manifest に INTERNET 権限なし。追加ライブラリ導入時も維持 |
| 可用性 | ネイティブエンジン欠落時にも UI は起動できる | エンジン状態の表示を用意。採譜は不可 |
| メモリ | 端末の RAM・ストレージを超える処理をしない | 長曲・モデルロードのピークを計測し、必要なら分割推論 |
| 性能 | 採譜中に UI スレッドを長時間占有しない | 単一ワーカーを使用。中断・段階的進捗は今後改善 |
| 端末差異 | MP3／MIDI デコーダ・音源差を考慮 | WAV 等も端末対応範囲で処理。MIDI 再生は実機確認必須 |
| 正確性 | 楽器分類、音価、発音時刻の誤検知を編集可能に | 手修正はあるが採譜品質の定量評価は未実施 |
| 同期 | 原盤と MIDI を比較可能にする | 250 ms 閾値の簡易補正。音出し開始レイテンシは未補正 |
| 保存 | 音符データの消失を抑える | 現行は単一 JSON 上書き。原子的保存・履歴は今後課題 |
| 出力 | 主要楽譜ソフトとの互換性 | XML 正当性の単体テストはあり、複数製品での読込未確認 |
| 法令・ライセンス | モデル・コードの権利条件を守る | 内包・再配布は許諾の確認をゲートとする |

## 12. テスト設計・受入条件

**既存テスト**：`tests/run-export-tests.sh` は JDK 上で `MidiExporter`／`MusicXmlExporter` をコンパイル・実行し、MIDI ヘッダー、XML パース・エスケープ、パート分離、重複音声部を確認する。これは Android 端末上の採譜や比較再生の合格を意味しない。

| ID | 試験 | 期待結果 |
|---|---|---|
| T-01 | クリーン clone → Wrapper ビルド | SDK／NDK 構成を満たす環境で APK が生成される |
| T-02 | オフライン起動 | ネットワーク権限なしで画面が起動する |
| T-03 | 原盤選択／再起動／権限変更 | Uri 再利用できる。失効時は明確な再選択案内 |
| T-04 | 10 分以下・超過・壊れた音声 | 正常音源は処理、超過と破損は明確なエラー |
| T-05 | MuScriptor ランタイム・GGUF の実機導入 | ABI・依存 .so・モデル読み込みが成功する |
| T-06 | ピアノ／ベース／ドラム混合音の採譜 | 楽器と音符時刻を表示。精度は評価基準と照合 |
| T-07 | 楽器フィルタ・音符編集・再起動 | 編集内容・BPM が保存される |
| T-08 | 全パート／個別パート MIDI 出力 | 楽器別トラックまたは選択楽器のみを出力 |
| T-09 | MusicXML 出力・外部ソフト読込 | パース可能、音符と小節構造を確認 |
| T-10 | 同時再生・共通停止・シーク | 原盤と MIDI が連動しクラッシュしない |
| T-11 | 片側 0%／ミュート／解除 | 他方の音量を維持し即時切替 |
| T-12 | 楽器／音符／BPM 変更後の再生 | 古い一時 MIDI を使わず再生成する |
| T-13 | アプリをバックグラウンドに移す | 一時停止し、戻って復帰可能 |
| T-14 | **モデル内包版** 初回起動 | 手動モデル導入なしでローカルモデルを配置し、採譜できる（未実装） |
| T-15 | **モデル内包版** 空き容量不足・中断・破損 | 明確なエラーと安全なリトライ、破損モデルを使わない（未実装） |
| T-16 | 非商用条件・配布物の監査 | モデル／依存ライブラリのライセンスと配布許可を確認（未完了） |

**受入判定の区分**：
- **ソース実装完了**：コンパイルと静的確認に合格。
- **MIDI／MusicXML 部分機能完了**：単体テストに合格。
- **アプリ動作完了**：対象 Android 実機で採譜から比較試聴・書出しまで成功。
- **モデル内包版完了**：T-14／T-15 を含む検証に合格。単なるアセット配置だけでは完了としない。

## 13. 開発優先度・未解決事項

1. **P0：推論エンジンの完成**。NDK クロスビルドと C ABI 対応、実機での MuScriptor Small 推論を成立させる。
2. **P0：権利確認**。モデルを内包・再配布する方法を決め、同意・表示・権利上の制約を満たす。
3. **P1：モデル内包化**。第 9 章のパッケージング・検証・コピー・エラー処理を実装し、通常の「モデルを追加」を不要にする。
4. **P1：比較再生の実機検証**。端末標準 MIDI プレーヤー、音色、発音遅延、停止／シーク後のずれを調査する。必要なら MIDI の PCM ソフトシンセ方式に切り替える。
5. **P1：安定性**。単一プロジェクトの原子的保存、長曲分割処理、キャンセルと進捗、メモリ計測。
6. **P2：楽譜品質**。テンポ・拍子推定、細かな音価・声部・連桁・打楽器譜を改善。
7. **P2：利便性**。楽器ごとの MIDI 一括保存、過去プロジェクト管理、比較再生オフセット調整。
