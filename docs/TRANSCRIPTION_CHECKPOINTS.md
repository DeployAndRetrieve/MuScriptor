# 採譜の分割・重複統合・途中保存・再開（v1.3.0）

更新日: 2026-11-28

## 状態

本仕様のJava/C++ソースを実装。30秒／5秒重複の分割・時刻補正・重複統合についてはホストJVM用のスモークテストを追加。Android向けAPKビルド・端末上のネイティブ推論・セッション再利用・音楽的精度は未検証。

## 1. 採譜区間

- **ウィンドウ長：30秒**
- **重複：5秒**
- **次の開始位置：25秒後**
- 例：第1区間 0–30秒、第2区間 25–55秒、第3区間 50–80秒
- 端数区間は原盤の末尾で切り詰め、不要な空白をパディングしない。
- 音声デコード後に16 kHzモノラルPCMのサンプル位置で区切る。整数サンプルに基づき連続性を保つ。
- 現行の10分上限の場合、最大24区間（開始位置0,25,…,575秒）。
- 一区間あたりのモデル生成上限は2000トークン（現在のJNI設定）。

## 2. マージ仕様

各区間で得られたイベントは、まず各区間の開始時刻を加算して**楽曲全体の絶対秒**に変換する。

隣の区間との5秒重複領域を照合し、次の条件を満たす音符同士を同一音符として統合する。

1. 楽器ID・MIDI音高が同じ。
2. 時間帯が重複し、短い側の音符長の55%以上が重なる。
3. 開始時刻の差が0.4秒以内か、新しい区間の冒頭で開始した「クリップされた音符」である。
4. 照合は隣接区間の重複領域に限定。1対1でマッチさせ、同一チャンク内部の音符は統合しない。

統合した場合の開始時刻は早い方、終了時刻は遅い方を使う。**新しいチャンクの先頭ちょうどで始まった音符は、前チャンクで確定した開始時刻を優先する**（25秒地点の切断によって発生した偽のオンセットを回避）。統合しない音符はそのまま残し、最終データを開始時刻・楽器・音高・終了時刻でソートする。

これは音符の時間重複に基づく**ヒューリスティックな統合**であり、楽器認識の変動・極端なテンポ・同音高の重奏・繰り返し音などで誤統合／二重音符／欠落の可能性がある。モデルの隠れ状態を引き継ぐことや、原曲と完全一致することは保証しない。

## 3. チェックポイント保存

保存ファイル：

`getFilesDir()/transcription-checkpoint.json`

保存形式はJSONで、次を同一ファイルに記録する。

| フィールド | 内容 |
|---|---|
| format | 書式バージョン |
| uri | SAFで選んだ音源のURI |
| fingerprint | デコードした全PCMのSHA-256 |
| model | APK内GGUFのSHA-256とサイズ情報 |
| samples | 原盤のPCMサンプル数 |
| sampleRate | 16000 |
| windowSeconds / overlapSeconds | 30 / 5 |
| nextChunk | 次に採譜する区間のインデックス |
| notes | 完了区間を統合した全音符イベント |

1区間の成功後に **音符データとnextChunkを同時にアトミック更新**。一時ファイルへ書込み、`FileDescriptor.sync()`後にファイルを置換する。

ネイティブ推論の途中でプロセスが落ちた場合、その区間の結果は失われるが、**最後に正常保存した区間までは残る**。読み込みに失敗するチェックポイントは勝手に上書きせず、ユーザーに通知する。

推論終了後は`project.json`を同じくアトミックに保存し、成功したらチェックポイントを削除する。途中経過中の音符編集は不可（再開時の統合による編集消失を防止）。途中経過は表示できる。

## 4. 再起動・停止

- 起動時のモデル検証完了後にチェックポイントがあれば、保存済みURIの一致を確認して**自動再開**。
- 再開時には原盤を再デコードしてPCMハッシュ、使用モデル、サンプル数を照合する。異なる場合は安全のため停止（旧データを自動消去しない）。
- ネイティブ推論は前回終了時の内部状態を復元するのではなく、**未完了の最初の区間から新規セッションで再実行**する。
- 「保存して一時停止」を押すと、現在のネイティブ区間が終了・保存された後に停止する。
- 「この曲を採譜」を押すと保存済み次区間から再開。
- 「最初から採譜」は、確認ダイアログの後に進捗を破棄し第1区間から開始。
- 別曲へ変更する際は、保存済み進捗を破棄するか確認を出す。
- アプリ画面の再作成時、実行中ジョブに再接続する。
- Androidによるプロセス強制終了やストレージ圧迫による停止は防げないが、確定済みチェックポイントは残る。
- **Foreground ServiceやWakeLockは未導入**。画面消灯中の実行保証はこの変更の対象外。

## 5. モデル・JNIライフサイクル

チャンクごとに400MB超のモデルを読み直すと大きな負荷になるため、NativeBridgeに次を追加。

- `nativeOpenAnalyzer(path)`：モデル・C APIセッションを一度だけ生成。
- `nativeAnalyzeChunk(handle, pcm, 16000, 2000)`：区間ごとに新規リクエストと結果を使い、**同じセッション**を再利用する。
- `nativeCloseAnalyzer(handle)`：正常・一時停止・エラー時を問わず`finally`で解放。

audio.cpp の C API はセッション再利用を想定しているが、**MuScriptor Smallでの24回連続実行は実機で確認する必要がある**。

## 6. テスト

ホストJDK21で、Android SDK不要のマージテストを実行：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\tests\Run-ChunkTests.ps1
```

macOS/Linuxでは`bash tests/run-chunk-tests.sh`。

チェック内容：30秒/5秒の区間計算、全体時刻への変換、境界をまたぐ音符の結合、繰返し同音高の保持、異なる楽器・音高の非統合、入力リスト不変性。

**追加で必要な実機受入試験：**

1. 原盤を採譜し、実際の音符データが区間ごとに保存されること。
2. 処理中にアプリをOSから終了させ、次回起動時に最後の区間から再開すること。
3. 5秒重複区間で二重音符を適切に除去し、境界をまたぐ持続音を保持すること。
4. 「一時停止」「最初から」「別曲へ変更」の動作と、チェックポイント破損時の診断。
5. MIDI/MusicXML生成・原盤/MIDI比較再生が統合データで動くこと。
6. Androidの省電力状態での処理時間、メモリ、CPU負荷。長時間処理の保証は別途FGS対応が必要。
